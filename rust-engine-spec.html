01 · Principios

Autoridad y límites.

El engine es la única autoridad para protocolo y estado. La plataforma ejecuta efectos; la aplicación expresa intención.

Determinismo

Misma historia, mismo estado

Con igual configuración, reloj, random y eventos, el reducer produce las mismas transiciones, efectos y reason codes.

Durabilidad

Commit antes de confirmar

Ninguna garantía de chunk, custodia, entrega u operación existe antes de la transacción correspondiente.

Transport independence

Radio reemplazable

BLE y Wi‑Fi implementan el mismo port. El modelo lógico no contiene clases ni errores propios de Apple o Android.

Bounded work

Nada ilimitado

Todo input, queue, mapa, timer, retry, parse y allocation tiene máximo local o negociado.

Opaque application

Payload sin acoplamiento

El core conoce namespace, policy y bytes; no conoce chats, rutas, pantallas ni modelos de Convoy.

Failure containment

El alcance importa

Un packet afecta enlace; un peer hostil se aísla; un store inconsistente detiene la sesión. No todo error derriba todo.

Fórmula del dominio: reduce(State, Input, Context) → Transition { new_state, effects, events }. Los effects nunca se ejecutan dentro del reducer.

03 · Tipos

Estados inválidos no se construyen.

Los valores externos se validan en builders. El dominio recibe newtypes y colecciones limitadas, no strings o mapas abiertos.

Identidad

MemberId identifica miembro lógico; PeerId identifica instalación/dispositivo autorizado; discovery aliases rotan y nunca sustituyen identidad.

Objeto

ObjectId se deriva del envelope canónico según la suite registrada. El relay conserva esos bytes exactos y no recodifica material firmado.

Tiempo

MonotonicInstant mide RTT, RTO y cooldown. HybridLogicalTimestamp ordena objetos. Wall clock solo entra mediante política de skew.

Overflow

Counters usan checked arithmetic. Agotar packet number obliga rekey; agotar sequence detiene el origen. Ningún contador hace wrap.

04 · Reactor

Un escritor; efectos externos.

El host crea un runner dedicado por runtime. El reducer nunca bloquea, duerme, abre sockets, lee DB ni consulta el reloj global.

pub trait Reducer {
    fn reduce(
        &mut self,
        input: EngineInput,
        ctx: &ReduceContext,
    ) -> Transition;
}

pub struct Transition {
    pub effects: BoundedVec<Effect, MAX_EFFECTS_PER_TICK>,
    pub public_events: BoundedVec<SdkEvent, MAX_EVENTS_PER_TICK>,
    pub next_deadline: Option<MonotonicInstant>,
}

pub enum EngineInput {
    Command(CommandEnvelope),
    Transport(TransportEvent),
    Store(StoreCompletion),
    Crypto(CryptoCompletion),
    Timer(TimerEvent),
    Lifecycle(PlatformLifecycleEvent),

MAILBOXPrioridad y orden estable

COMPLETIONResultado correlacionado vuelve

Mailbox

Control, lifecycle y completions durables no compiten en igualdad con bulk. Capacidad llena devuelve presión; no descarta comandos durables.

Ordering

Cada input recibe LocalEventSeq. Empates de deadline se resuelven por clase y secuencia, nunca por orden de hash map.

Effects

Cada effect lleva EffectId, operation, deadline y cancel token. Completions tardíos se reconocen y descartan de forma determinista.

Workers

Store y crypto usan pools acotados. Ningún worker comparte estado mutable del engine; recibe valores inmutables y devuelve resultados.

Snapshot

El SDK obtiene snapshot + cursor dentro del mismo tick. Eventos posteriores tienen secuencia mayor y no existe ventana de pérdida.

Shutdown

DRAIN acepta solo control y completions; PERSIST checkpoint y detiene radios; ABORT queda reservado a fatal interno.

06 · Máquinas de estado

Transiciones explícitas.

Cada máquina define eventos aceptados, timeout, side effects y razón de salida. Estados imposibles no se representan con combinaciones de booleanos.

Runtime

NEW → OPENING_STORE → READY → RUNNING → DRAINING → STOPPED
RECOVERING y FATAL son ramas explícitas. Solo READY/RUNNING aceptan comandos de aplicación.

Group session

IDLE → PREPARING → STARTING → ACTIVE, subestados DEGRADED, ISOLATED, SUSPENDING, SUSPENDED, RECOVERING.

Peer security

UNKNOWN → CERT_CHECK → NOISE_HANDSHAKE → AUTHENTICATED → REKEYING → CLOSED. Cualquier fallo de autenticidad termina en REJECTED con cooldown.

Link

DISCOVERED → PROBING → AUTHENTICATING → WARM → ACTIVE → DEGRADED → LOST → COOLDOWN. El link no posee la identidad del peer.

Durable object

BUILDING → COMMITTING → QUEUED → REPLICATING → CUSTODIED → SATISFIED. También EXPIRED, CANCELLED o QUARANTINED.

Inbound object

ANNOUNCED → REQUESTED → PARTIAL → COMPLETE → VERIFIED → COMMITTED → DELIVERED. DELIVERY se deduplica en la misma transacción.

Interactive stream

OPENING → ACTIVE → DRAINING → CLOSED. INTERRUPTED es terminal para esa instancia; fallback durable crea una operación distinta.

Operation

ACCEPTED → RUNNING → SUCCEEDED / FAILED / CANCELLED. El resultado final queda ligado a idempotency key para recovery.

Prohibido: reconstruir máquinas desde callbacks nativos aislados. Todo callback entra como evento y la transición solo ocurre en el reactor.

07 · Pipelines

Orden de seguridad y commit.

Estas secuencias son normativas. Cambiar su orden requiere ADR porque altera garantías frente a crash, replay o corrupción.

Outbound durable

  1. Validar namespace, audiencia, contrato, TTL y cuota.
  2. Resolver ROLE a member set inmutable.
  3. Reservar origin sequence e idempotency key.
  4. Generar content key/nonce desde CSPRNG.
  5. Codificar header canónico y cifrar payload.
  6. Firmar material normativo.
  7. Fragmentar y calcular manifest/hashes.
  8. Commit objeto + chunks + operation + outbox.
  9. Emitir Accepted solo tras commit.
  10. Planificar relays y transportes.

Inbound frame

  1. Aplicar máximo físico antes de copiar.
  2. Framing incremental con budget CPU.
  3. Resolver sesión autenticada.
  4. Verificar packet number/replay window.
  5. AEAD open; fallo descarta y penaliza.
  6. Validar CBOR canónico y límites.
  7. Despachar control/chunk sin recodificar.
  8. Actualizar ACK y métricas.

Inbound object

  1. Validar anuncio, audience epoch y lifetime.
  2. Responder WANT con ranges/bitmap.
  3. Verificar cada chunk y manifest.
  4. Commit de chunk antes de CHUNK_COMMIT.
  5. Al completar, verificar object ID y firma.
  6. Descifrar solo si somos destinatario.
  7. Commit objeto + custody + delivery marker.
  8. Emitir custodia y evento de app después.

Reencuentro

  1. Validar alias rotativo y epoch.
  2. Seleccionar XX o IK según confianza.
  3. Negociar suite y capabilities.
  4. Crear session keys y packet space nuevos.
  5. Intercambiar inventory summaries.
  6. Calcular missing ranges.
  7. Reanudar chunks pendientes.
  8. Actualizar score solo con mediciones reales.

08 · Scheduler

ASAP sin starvation.

La prioridad no es una cola única. Admission, fairness, flow control, routing y transport selection son pasos separados.

effective_goodput = ewma_delivered_bytes / ewma_active_time
retransmission_risk = loss_weight * expected_retries * rtt_penalty
eta = setup_remaining + pending_bytes / max(effective_goodput, floor) + retransmission_risk

neighbor_score = health + coverage_diversity + stability + custody_reliability - congestion
forward_score  = link_health + coverage_gain + custody_history - queue_pressure - duplicate_risk
EtapaAlgoritmoGarantía
AdmissionReserva por clase y cuota por app/grupo/peerControl conserva capacidad bajo bulk
Class selectionCONTROL > INTERACTIVE; luego weighted deficit round robinBulk/background progresan sin bloquear urgente
Object selectionDeadline + age boost + remaining costObjetos viejos reciben prioridad gradual
Peer selectionForward score y audience needNo se replica donde no hay ganancia
Transport selectionETA por peer/perfilWi‑Fi no gana si setup supera transferencia BLE
Flow controlCredits de enlace + ventana de bytes inflightReceptor controla memoria
Relay staggerMejor peer inmediato; segundo ≈150 ms sin durable progressRedundancia controlada, no flooding

Health

Healthy ≥70, usable 50–69, degraded <50. Fast EWMA ≈2 s detecta cambio; slow EWMA ≈10 s evita reaccionar a ruido.

Soft switch

Candidato saludable 2 s y ETA al menos 25% mejor; make-before-break y hold-down 5 s.

Hard fail

Error adapter, crypto inválida, peer perdido, 3 RTO o 2.5 s sin progreso. Cooldown 2/5/10 s, reset tras 30 s estable.

09 · Persistencia

Transacciones como protocolo.

El store de referencia usa SQLite cifrado con WAL. Object ciphertext protege contenido; DB encryption protege metadata local.

outbox(effect_id PK, object_id, peer_id, transport_hint, state, retry_at)
schema_migrations(version PK, checksum, applied_at)

Atomicidad outbound

Object, chunks, operation y outbox se insertan juntos. Si falla el commit, no se emite Accepted y repetir la idempotency key es seguro.

Atomicidad inbound

Chunk bytes y bitmap cambian juntos. Objeto completo, custody y delivery marker comparten transacción para impedir doble entrega.

Compaction

Solo elimina datos cuyo contrato, retención y evidencia permiten descarte. Tombstones/receipts mínimos se conservan para dedupe.

Pressure

Soft threshold frena BACKGROUND/BULK; hard threshold rechaza admission nueva. Nunca borra automáticamente identidad o pendientes críticos.

Corruption

Registro inválido pasa a quarantine con reason code. Índices derivados se reconstruyen; material firmado no se repara modificándolo.

Migrations

Forward-only, transaccionales e idempotentes. Fixtures de cada versión soportada prueban upgrade, crash intermedio y reapertura.

10 · Seguridad · A010

Jerarquía, suite y recovery normativos.

El engine aplica una suite única y fail-closed: Ed25519, X25519, HKDF-SHA-256, SHA-256, ChaCha20-Poly1305, Noise XX/IK y HPKE por destinatario. La plataforma custodia claves; Rust controla contexts, transcripts, epochs, nonces, replay, envelopes, revocación y recovery.

Domain separation

Typed labels cubren certificate, object, receipt, transition, recovery, discovery y HPKE context. Una API no acepta label libre.

Nonce safety

Object base nonce + checked chunk index; traffic nonce desde packet number. Overflow cierra operación/link antes de reuse.

Anti-replay

Packet window por session incarnation, invitation use record, object ID dedupe y recovery counter monotónico.

Downgrade

Suite, wire y capabilities quedan en transcript firmado. Sin intersección produce error terminal, nunca fallback débil.

Secret types

No Clone/Debug/Serialize, exposición por closure mínima y zeroization. Telemetry solo recibe aliases y key IDs.

Blind relay

Verifica envelope, firma, digest, epoch y policy; content key solo se abre cuando local member pertenece al snapshot.

HPKE, no MLS activo: el recipient-wrap lineal es la decisión normativa para el grupo actual y tolera particiones sin árbol/commit global. CryptoProvider preserva extensibilidad, pero cambiar provider exige nueva suite, ADR, migration y conformance vectors.

11 · ABI / FFI

Bytes y handles, no layouts Rust.

La ABI C es deliberadamente pequeña. Los envelopes CBOR de API están separados del wire mesh y llevan su propia versión.

typedef struct { const uint8_t *ptr; size_t len; } mesh_slice_t;      /* borrowed */
typedef struct { uint8_t *ptr; size_t len; size_t cap; } mesh_buffer_t; /* owned */
typedef struct { int32_t code; uint32_t detail; } mesh_status_t;

Ownership

Borrowed input es válido solo durante llamada. Todo output se libera con la misma library. No se mezclan allocators Swift/Kotlin/Rust.

Handles

Índice + generación detecta stale handles y ABA. Release es idempotente a nivel host; uso posterior devuelve INVALID_HANDLE.

Threading

submit/notify son thread-safe y no bloquean por I/O. poll pertenece al runner designado o usa wake callback mínimo.

Unwind

Ningún panic o excepción cruza ABI. catch_unwind en frontera de worker convierte panic recuperable en ENGINE_FATAL; OOM sigue siendo fatal de proceso.

Compatibility

Host consulta ABI antes de crear runtime. Major incompatible aborta inicialización con mensaje accionable; nunca intenta interpretar memoria.

Unsafe budget

Cada función unsafe documenta precondiciones, valida null/length/alignment y entra inmediatamente a una abstracción safe.
